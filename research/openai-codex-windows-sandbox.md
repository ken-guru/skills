## 2. What the article describes

Codex on Windows runs commands with full user permissions by default. The stated design goal (quoted, reader-proxy fetch): "allow Codex to read files almost anywhere and write files within your workspace... with no internet access unless you specify you want it."

**Three existing Windows mechanisms were evaluated and rejected:**

- **AppContainer** — "the native Windows sandbox, a capability-based isolation model built for apps that know, up front, exactly what they need to access." Rejected because Codex is not one tightly-scoped app: it "drives open-ended developer workflows: shells, Git, Python, package managers, build tools, and whatever other binaries the agent decides it needs" — a workload whose subprocess/capability needs are decided at runtime by the agent, not declared upfront.
- **Windows Sandbox** — a disposable, isolated VM. Rejected because "Codex needs to act directly on the user's actual checkout, tools, and environment, not inside a separate throwaway desktop" — i.e., true VM-level isolation solves a different problem (an ephemeral environment) than the one Codex has (mutating the developer's real, persistent checkout).
- **Mandatory Integrity Control (MIC)** — labeling the workspace "low integrity" so only low-integrity processes can write there. Rejected because "low-integrity processes in general can write there" — the label isn't scoped to Codex specifically, so it converts the workspace into a shared low-integrity sink for anything else running at low integrity, not a Codex-specific boundary.

**The design that shipped, in two stages:**

1. **Unelevated prototype.** A synthetic `sandbox-write` SID plus a *write-restricted token* — quoted: "A write-restricted token is a particular type of process token that makes Windows perform an additional access check on write operations," requiring both that "the normal user identity (the token 'owner') must be allowed to do it" *and* "at least one SID in the token's restricted SID list must also be granted access." The `sandbox-write` SID is granted write/execute/delete on the current working directory and any configured `writable_roots` (from `config.toml`), with explicit denials on `<cwd>/.git`, `<cwd>/.codex`, and `<cwd>/.agents` — i.e., write access is denied by default and allowlisted per-path, including carving out the agent's *own* control/audit directories from the write grant even though they sit inside the otherwise-writable workspace. Network denial in this stage used environment variables (e.g., `HTTPS_PROXY` pointed at a dead local port); this was abandoned as merely "advisory," since it could "definitely be circumvented by some programs" that don't honor proxy env vars or that open raw sockets directly.
2. **Elevated production design.** Adds dedicated local Windows accounts (`CodexSandboxOffline`, `CodexSandboxOnline`) and Windows Firewall rules that block all outbound traffic for the offline account at the OS network-stack level — enforcement that holds regardless of whether the spawned tool respects any proxy convention. Credentials for these accounts are protected via DPAPI. Execution is split across purpose-built binaries — `codex.exe` (unelevated harness) → `codex-windows-sandbox-setup.exe` (one-time elevated setup: create SIDs, accounts, firewall rules) → `codex-command-runner.exe` (per-command: calls `CreateProcessWithLogonW` to launch as the sandbox user, then `CreateRestrictedToken` to build the final restricted token before `CreateProcessAsUserW` spawns the actual child) — explicitly to keep "Windows-only setup machinery from bloating `codex.exe` on other platforms," and to keep the elevated, higher-privilege code path (setup) separate from and much smaller than the per-command unprivileged execution path.

Closing line (quoted): "Each piece of complexity was added out of necessity, to build a sandbox that is both safe and, as much as possible, not in the user's way."

## 3. Principles extracted (generalized past the Windows-specific mechanism)

1. **Match the isolation mechanism's shape to the workload's shape, not the other way around.** AppContainer is a capability-declared-upfront model; Codex is an agent that decides its own subprocess tree at runtime. A sandbox built for narrow, pre-scoped apps is the wrong shape for an open-ended agent, independent of how strong its isolation is. *(Source: §2, AppContainer rejection.)*
2. **Read broadly, write narrowly and explicitly allowlisted — including carving the agent's own control-plane directories out of its own write grant.** Default is read-mostly-open, write-closed; writes are allowlisted to the workspace plus configured extra roots, and even within the writable workspace, the agent's own state directories (`.git`, `.codex`, `.agents`) are explicitly denied. *(Source: §2, unelevated prototype, SID/ACL design.)*
3. **Enforce at a boundary that arbitrary, unknown subprocesses cannot opt out of — not at a convention an obedient process could ignore.** The move from `HTTPS_PROXY`-based network denial to Windows Firewall rules was driven specifically by the fact that Codex spawns package managers, build tools, and other binaries the agent chooses at runtime, which cannot be trusted to honor a proxy environment variable or a denylist path; only OS-level (kernel/network-stack) enforcement holds for all of them uniformly. *(Source: §2, network section.)*
4. **Separate the smallest possible elevated/high-privilege code path from the much larger unprivileged per-command execution path.** One-time elevated setup (accounts, SIDs, firewall rules) is isolated in its own binary; every actual command execution runs through an unprivileged harness plus a purpose-built restricted-token spawner. *(Source: §2, elevated design, three-binary split.)*
5. **Real isolation must act on the user's actual environment, not a disposable copy — full VM-style isolation was rejected for solving the wrong problem.** Windows Sandbox's strong isolation was rejected not because it's weak, but because Codex needs to mutate the developer's real checkout, tools, and environment, and a throwaway VM would only isolate a copy. *(Source: §2, Windows Sandbox rejection.)*

## 4. Compared against what this repo already has / has already decided

Checked `skills/setup-devcontainer/` (`CONTEXT.md`, `SKILL.md`, `docs/adr/*.md`) for existing sandboxing/containment/hardening content, and the precedent research at `research/codex-bubblewrap-sandbox-permissions.md` (the sibling ticket, #212, on Codex's *Linux* sandbox):

- **Principle 1 (match mechanism to workload shape) is already the exact reasoning behind this repo's own [ADR-0002](../skills/setup-devcontainer/docs/adr/0002-collapse-tool-container-isolation.md):** per-tool isolated containers (the AppContainer-like narrow model) were tried and explicitly abandoned in favor of one open-ended Shared Container, because the isolated-container era's real, measured cost (535-line SKILL.md, ~1142 lines of scripts, 8 devcontainer.json variants) outweighed its isolation benefit for a workload whose tool needs are open-ended per-CLI. OpenAI's Windows article independently arrives at the same shape-matching principle for the same underlying reason (open-ended developer tooling doesn't fit a narrow, pre-scoped isolation model) — this **confirms**, but does not change, a decision this repo already made.
- **Principle 2 (read-broadly/write-allowlisted-to-workspace, including denying the agent's own control directories) is already what Codex's own *Linux* sandbox does**, per the precedent bubblewrap research: Codex's `linux-sandbox` mounts writable roots explicitly and everything else read-only or masked, using the same "workspace + configured writable_roots" shape the Windows article describes. This is not new information for a decision about `skills/setup-devcontainer` specifically — it is a property of Codex's own per-command sandbox (which the CLI brings itself, on whichever platform), not something this repo's devcontainer generation configures. There is nothing in `skills/setup-devcontainer`'s generated files that a `.git`/`.codex`/`.agents`-style write-carve-out would attach to; that carve-out lives inside each AI CLI's own sandboxing tool, not the shared container boundary.
- **Principle 3 (enforce network denial at the OS/kernel layer, not via proxy env vars, because arbitrary subprocesses won't honor conventions) is a real, generalizable point, but it is not new relative to what this space already knows.** `skills/setup-devcontainer` currently configures **no network egress control at all** (confirmed by grep — no firewall/iptables/egress content anywhere in the skill). The specific Linux realization of "enforce network denial at the OS layer, not at the app-convention layer" (an iptables/ipset-based egress-allowlist firewall script run at container startup) is the well-known pattern from Anthropic's own reference Claude Code devcontainer — which is the explicit subject of the parallel Anthropic-sandboxing research ticket referenced in #281. OpenAI's Windows article reaches the identical principle independently (proxy-env-var denial is advisory and bypassable; only kernel/network-stack-level blocking holds), which is a nice independent confirmation that the principle is sound, but it supplies no Linux-specific technique, tool, or detail beyond what that parallel ticket is already expected to surface.
- **Principles 4 and 5** (elevated-setup/unprivileged-execution split; real environment vs. disposable copy) are Windows-privilege-model and VM-vs-native distinctions specific to problems this repo's Docker-based devcontainer doesn't have in the same form (Docker already runs each container as a single, mostly-fixed privilege level chosen once at container build/run time, not per-command; and the devcontainer already acts on the user's real bind-mounted checkout, which is the "act on the real environment, not a copy" choice already made). Nothing actionable here beyond what's already true of the existing architecture.

## Bottom line

**No transferable action for `skills/setup-devcontainer`'s Linux/Docker devcontainer beyond confirming principles this repo (or the parallel Anthropic-sandboxing research) already has covered.** Every principle in the OpenAI Windows sandbox article that generalizes past Windows-specific mechanism (SIDs, restricted tokens, ACLs, `CreateProcessWithLogonW`, Windows Firewall per-account rules) maps onto a decision this repo has either already made (ADR-0002's shared-container-over-narrow-isolation choice, directly paralleling the AppContainer rejection), already delegates to each AI CLI's own sandbox rather than the shared devcontainer (Codex's own Linux bubblewrap sandbox already implements the read-broad/write-narrow-allowlisted model, per the sibling `research/codex-bubblewrap-sandbox-permissions.md` finding), or is the well-known subject of a parallel research ticket (OS-level/kernel-enforced network egress denial, which is exactly what Anthropic's own reference devcontainer's iptables-based firewall script already does, and what the parallel Anthropic-sandboxing ticket for #281 is expected to cover in Linux-specific detail). This source is useful as independent, first-party corroboration that "mediate access at a boundary arbitrary subprocesses can't opt out of" and "default-deny writes/network, then allowlist" are sound, convergently-discovered principles — not as a source of any new Linux-actionable technique for this repo's Baseline Containment work under #281.
