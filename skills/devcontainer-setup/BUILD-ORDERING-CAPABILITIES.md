# Build-time network access vs. runtime-firewalled network access

If your devcontainer runs an outbound firewall (an allowlist of known-good domains, applied by a script that runs on container start), that firewall does not exist yet during the image build, and it does not exist yet during whatever setup step runs before the firewall script itself executes. This gives every setup step exactly two safe places to reach the open internet from: build time, before the firewall is even a concept, or runtime, after the firewall exists, with the exact destination host added to its allowlist first. There is no safe third option where a step "temporarily" bypasses the firewall or races it.

Treat this as load-bearing, not a style preference. The classic way to discover it the hard way: install your firewall's own dependencies (the packages that let it manage netfilter rules at all) via a runtime package-manager call in your setup script. The first time the firewall starts enforcing on every container start, that same package-manager call starts failing, because the firewall it depends on existing has now blocked the package mirror it needs to reach. The fix is not a firewall exception for the mirror; it's moving that install into the image build, a phase with no firewall at all. Any step that needs broad, unpredictable network access, an OS package mirror, a browser-automation vendor's binary CDN, a CLI's release-asset host, belongs at build time or in the earliest runtime setup step, never in a step that runs after the firewall initializes, unless its destination is explicitly allowlisted first.

A related trap: don't assume a floating base-image tag is safe just because it resolves at build time. If you pin your image to a moving target (a distribution's "latest" alias rather than a specific release codename), the tag can drift out from under you between rebuilds, and some of your vendored tooling may not have caught up. A concrete version of this: a browser-automation framework's browser-binary distribution can lag a brand-new OS codename by months, publishing builds for the prior codename only, on some architectures. If your base image floats past that boundary, an install step that worked yesterday fails today with no code change on your side. Pin to the exact codename you've verified against your dependencies' own release matrices, and re-verify that matrix deliberately when you choose to move the pin, rather than letting it move on its own.

One more instance of the same instinct, in a smaller and easier-to-miss form: keep a general-purpose scripting runtime installed even if nothing in your own repository's scripts calls it, when the container's real users include an AI coding agent that reaches for a quick inline script mid-session. A dependency audit that only greps your own scripts for usage will miss this consumer entirely, because its usage is by design never committed anywhere. Document the reasoning inline where the package is installed, so the next audit doesn't remove it for looking unused.

# Capability scoping for nested sandboxing

If a tool running inside your devcontainer needs its own nested sandbox (a namespace-based process isolation tool, for instance), it will typically need one or two specific Linux capabilities and a relaxed seccomp or filesystem-path profile, not full container privilege. Reach for `privileged: true` and you grant every capability and device the kernel has, not just the two or three the nested sandbox actually touches; reach for the narrow grant instead and the blast radius of a compromised nested process stays bounded to what you explicitly named.

Two closely related patterns show up together often enough to name separately: a firewall running inside the container needs `NET_ADMIN` and `NET_RAW` to manage its own netfilter rules, while a nested process-sandboxing tool typically needs `SYS_ADMIN` plus an unconfined seccomp profile and unconfined system paths, because creating a user namespace and then mounting a private filesystem tree inside it is a privileged operation that some container runtimes (notably ones running on top of a lightweight Linux VM rather than bare-metal Linux) can't satisfy through the usual AppArmor escape hatch. Grant exactly those, comment each one inline with which nested tool needs it and why, and add a startup health check that actually exercises the nested sandbox (create the namespace, mount, pivot root) rather than just checking the binary exists, so a capability regression surfaces immediately as a clear failure instead of a confusing error buried in whatever the nested tool was trying to do.
