# How `npx skills` and skills.sh install and identify a Skill's version

Research note for [#425](https://github.com/ken-guru/skills/issues/425) (map [#424](https://github.com/ken-guru/skills/issues/424)). Facts only, no recommendations.

## 1. What gets installed: default branch HEAD, or a ref

- **Default is the default branch HEAD.** With no ref, `cloneRepo` runs `git clone --depth 1` with no `--branch`, so it gets the remote's default branch (`SRC/src/git.ts`, `cloneRepo`, around line 301).
- **A ref can be given as a URL fragment: `#<ref>`.** `parseFragmentRef` treats `owner/repo#<ref>` (and `#<ref>@<skill>`) as a git ref on git-like sources (`SRC/src/source-parser.ts`, around lines 284–314). Tests cover `vercel-labs/agent-skills#feature/install` and `git@github.com:owner/repo.git#feature/install` (`SRC/src/source-parser.test.ts`, lines 128–148). A GitHub `/tree/<ref>/<path>` URL also sets the ref, and so does Azure Repos `?version=GB<branch>`/`GT<tag>`.
- **Branches and tags work, and so does a full 40-char commit SHA.** The ref goes to `git clone --depth 1 --branch <ref>`, which takes a branch or a tag. If that fails and the ref is a full SHA, the CLI retries with `git fetch --depth 1 origin <sha>` and `checkout FETCH_HEAD` (`SRC/src/git.ts`, `isCommitSha`, `cloneAtSha`, lines 20–76 and 311–318). The lock-file comment calls the field "Branch or tag ref" (`SRC/src/skill-lock.ts`).
- **`@` selects a Skill, not a version.** `owner/repo@<name>` sets `skillFilter` (`SRC/src/source-parser.ts`, around line 529; `ParsedSource.skillFilter` in `SRC/src/types.ts`). So `ken-guru/skills@1.2.0` would look for a Skill named `1.2.0`. The README uses `@` only as a skill selector (`npx skills use vercel-labs/agent-skills@web-design-guidelines`).
- **No semver resolution.** Nothing resolves a version range or looks up the "latest tag". A ref is passed to git as given.
- **skills.sh blob fast path (not used for this repo).** For GitHub sources whose owner is on `BLOB_ALLOWED_OWNERS` (`vercel`, `vercel-labs`, `heygen-com`, `remotion-dev`) or whose repo is on `BLOB_ALLOWED_REPOS`, `add` first tries to download pre-built snapshots from `https://skills.sh/api/download/<owner>/<repo>/<slug>` and clones only if that fails (`SRC/src/add.ts`, around lines 1368–1390; `SRC/src/blob.ts`). The code says these snapshots are "keyed only by owner, repository, and skill slug. They are not bound to the requested ref", so an explicit ref skips the fast path (`tryBlobInstall`, `SRC/src/blob.ts`). `ken-guru` is not on either list, so `npx skills add ken-guru/skills` always clones.

## 2. Version fields, lockfiles, and manifests

- **No version is read from `SKILL.md`.** The frontmatter parser returns raw YAML (`SRC/src/frontmatter.ts`). The only fields the CLI reads are `name`, `description` and `metadata.internal` (`SRC/src/skills.ts`, around lines 115–131; `SRC/src/blob.ts`). No non-test source reads `version` or `metadata.version`. The README lists `name` and `description` as required and `metadata.internal` as the only optional field it acts on. The `Skill` type keeps the whole `metadata` object but does nothing else with it (`SRC/src/types.ts`).
- **Global installs (`-g`) write `~/.agents/.skill-lock.json`**, or `$XDG_STATE_HOME/skills/.skill-lock.json` when `XDG_STATE_HOME` is set (`SRC/src/skill-lock.ts`, `getSkillLockPath`). The schema is version 3, and an older lock file is discarded without migration. Each Skill entry holds `source`, `sourceType`, `sourceUrl`, `ref` (only when one was given), `skillPath`, `skillFolderHash`, `installedAt`, `updatedAt`, and optionally `pluginName`, `sourceBaseUrl` and `wellKnownDigest`.
  - For GitHub sources, `skillFolderHash` is the **git tree SHA of the Skill's folder**, fetched through the GitHub Trees API for the given ref, or for `HEAD`/`main`/`master` when there is none (`SRC/src/add.ts`, around lines 2093–2133; `SRC/src/blob.ts`, `fetchRepoTree` and `getSkillFolderHashFromTree`). For other sources it is a SHA-256 over the files on disk (`computeSkillFolderHash` in `SRC/src/local-lock.ts`).
  - **The commit SHA is not recorded.** Neither is any version string.
- **Project installs (no `-g`) write `./skills-lock.json`**, which is meant to be committed (`SRC/src/local-lock.ts`, schema version 1). Each entry holds `source`, `sourceUrl?`, `ref?`, `sourceType`, `skillPath?` and `computedHash`, which is a SHA-256 over the Skill folder's file contents, plus the optional `subagents` and `wellKnownDigest`. Entries have no timestamps, commit SHA or version.
- **`skills list` shows name, path, agents and `source`.** It shows no ref, hash or version (`SRC/src/list.ts`, around lines 147–170).
- **Install telemetry** (`https://add-skill.vercel.sh/t`) sends `source`, Skill names, agents, `global`, `skillFiles` (name → path) and optional `metadata`. It sends no ref, commit or version (`SRC/src/telemetry.ts` `InstallTelemetryData`; `SRC/src/add.ts`, around lines 2040–2064).

## 3. `skills update`: compares content hashes, not versions

- **Global** (`updateGlobalSkills`, `SRC/src/update.ts`, around lines 489–737): entries are grouped by `source` plus `ref`. For GitHub sources, the CLI fetches the repo tree at the recorded `ref` (or HEAD) and compares each Skill folder's tree SHA with the stored `skillFolderHash`. Otherwise it clones at the ref and compares a git tree hash or a content hash. A Skill counts as changed when the hashes differ. It is then updated by re-running `skills add <sourceUrl[#ref]> --skill <name> -g -y` as a child process, which overwrites the installed copy.
- **Entries `update` skips:** `sourceType` `local`, `git` or `well-known`, or no `skillFolderHash`/`skillPath`. It reports these with reasons such as "Git URL", "Private or deleted repo" and "No version tracking" (`getSkipReason`, `SRC/src/update.ts`, lines 186–203).
- **Project** (`updateProjectSkills`, around lines 739–990): the CLI clones at the recorded ref, computes a SHA-256 over each Skill folder, and reinstalls only when that differs from `computedHash`.
- **A pinned ref stays pinned.** `update` re-fetches the same ref. For a tag, that means no change unless the tag moves. Nothing looks for a newer tag or version.
- **Plain `skills add` does not compare anything.** The installer wipes the target directory and rewrites it (`cleanAndCreateDirectory`, `SRC/src/installer.ts`, around line 193).
- The README describes `update` as "Update installed skills to latest versions". The skills.sh FAQ says "Run npx skills update to pull the latest versions … New installs always fetch the current contents." In both cases "version" means the current upstream content.

## 4. What skills.sh shows for each Skill

- **Skill page** (for example [/ken-guru/skills/unslop](https://skills.sh/ken-guru/skills/unslop)): an install command (`npx skills add https://github.com/ken-guru/skills --skill unslop`) plus a "Prompt" variant using `npx skills use`, a summary, the rendered `SKILL.md`, **Installs** (a count), **Repository**, **GitHub Stars**, **First Seen** (a date, "Aug 21, 2026" for unslop), and **Security Audits** (Gen Agent Trust Hub, Socket, Snyk: pass or warn). The page shows **no version, no commit and no last-updated date**. Its schema.org `SoftwareApplication` JSON-LD has no `softwareVersion` or `dateModified`.
- **Repo page** ([/ken-guru/skills](https://skills.sh/ken-guru/skills)): Skill count (14), total installs (663), and install counts for each Skill. No version is shown.
- **Download API** (`/api/download/<owner>/<repo>/<slug>`): returns `{ files, hash }`, where `hash` is "SHA-256 hash of the skill's file contents. Use for cache invalidation or detecting changes" ([/docs/api](https://skills.sh/docs/api)). For `ken-guru/skills/unslop` it returned three files and `hash` `0b3b3b91…`. The response has no ref or commit.
- Per [/docs](https://skills.sh/docs), the leaderboard ranks Skills by anonymous CLI install telemetry.

## 5. This repo's setup-*-devcontainer Skill sync

- Each CLI Skill renders one line per source into `.devcontainer/post-start.sh`, so it runs on every container start:
  `npx -y skills add <source> --skill '*' -a <agent> -y --copy -g`, or `--skill '<name>'` for a single Skill. The `<agent>` values are `claude-code`, `codex`, `github-copilot` and `antigravity-cli`. See step 5 or 6 of each `skills/setup-{claude,codex,copilot,antigravity}-devcontainer/SKILL.md`. Sources are `mattpocock/skills`, `ken-guru/skills` or `owner/repo/skill-name`, each checked first with `npx -y skills add <source> --list`.
- **Nothing is pinned.** The `skills` CLI itself runs through `npx -y skills` at whatever version npm serves, and sources have no `#ref`, so every start installs the default branch HEAD. (ken-guru is not on the blob allowlist, so this is a `git clone --depth 1`.)
- **Wiping:** the Claude block runs `rm -rf /home/vscode/.claude/skills/*` before syncing (`skills/setup-claude-devcontainer/templates/post-start-block.sh`). The Codex, Copilot and Antigravity blocks write to the shared `~/.agents/skills` and do not wipe it, so a Skill removed upstream stays installed (their `templates/post-start-block.sh`).
- **What is already recorded:** because every sync uses `-g`, the CLI writes `~/.agents/.skill-lock.json` (per section 2), holding each Skill's `source`, `sourceUrl`, `skillPath`, folder tree SHA, `installedAt` and `updatedAt`, but no commit SHA or version. `/home/vscode` is the `{{REPO_NAME}}-config` named volume (`skills/setup-devcontainer/templates/devcontainer.json`), so this lock file lasts across container rebuilds. The post-start blocks do not read it, write any other record, or log what they installed.
- **What the sync could record without changing the CLI:** the global lock file above, and the `add` command's `--json` output. `add` builds a content hash for each installed Skill for `--json` (`SRC/src/add.ts`, around lines 2066–2080). For a commit SHA, the only mechanism the CLI offers is passing `#<sha>` or `#<tag>` in the source. It never reports the commit it resolved HEAD to.
- `skills/setup-devcontainer/scripts/check-skill-sync-targets.sh`, run by the scheduled `setup-devcontainer-skill-sync-drift.yml` workflow, checks only where `skills add` writes for each `-a` flag. It does not check versions.
