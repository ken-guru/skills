# Staged activation for MCP servers, and multi-CLI config wiring

## Installing the agentic CLIs themselves is a different case from installing their MCP servers

Everything below covers installing and updating *MCP servers* a CLI connects to. Installing the *CLI binaries themselves* (Claude Code, Codex, Gemini CLI, Cursor CLI, or similar, via `npm install -g <package>`) is a related but distinct need, and it's a very likely companion step whenever a devcontainer wires up agentic tooling at all, since a container that talks to MCP servers almost always needs at least one CLI installed to drive them.

It hits a different failure mode than anything the stage/verify/swap pattern below addresses: `npm install -g` as the container's non-root user fails immediately with `EACCES`, because the default global-install prefix on most base images is writable only by root. The staged per-server installs described below sidestep this already, since they use a scoped `--prefix` pointed at a private staging directory, but a plain `npm install -g` for the CLI binary itself has no such scoping unless you add it. Set `NPM_CONFIG_PREFIX` to a directory under the non-root user's home directory, and put that directory's `bin` subdirectory on `PATH`, before any global npm install runs, whether that's in the Dockerfile or a runtime setup hook. See the non-root-user block in [`Dockerfile.skeleton`](templates/build/Dockerfile.skeleton) and the npm-prefix gotcha in [BUILD-ORDERING-CAPABILITIES.md](BUILD-ORDERING-CAPABILITIES.md) for the concrete fix.

## The reliability technique: stage, verify, atomic-swap

When a development container wires up Model Context Protocol (MCP) servers for one or more agentic coding CLIs, the naive approach is to let the CLI resolve the server package at launch time, often via `npx <package>` or an equivalent "just fetch and run" mechanism. This works until it doesn't: `npx` resolves whatever the npm cache or registry hands back at that exact moment, which means the server version an agent gets is effectively unpinned and unreviewable. A supply-chain compromise of the package, or simply a breaking release landing between two sessions, becomes something the agent discovers by failing mid-task rather than something a maintainer reviewed and approved in advance.

The fix is a general reliability pattern, not specific to MCP: **stage, verify, then atomically swap.**

1. **Stage.** Install the candidate version into a private, uniquely-named directory, never directly over the location a running process might be reading from. Use an explicitly writable, isolated package-manager cache for this install so it can't be poisoned by or interfere with anything else on the machine.
2. **Verify.** Before the candidate is eligible to become active, prove it actually works, not just that the install command exited zero. For an MCP server specifically, this means completing a real protocol handshake: spawn the candidate, send an `initialize` request over its stdio transport, and confirm a well-formed response (a protocol version string, a server-identity string, on the matching request id) before completing the handshake with the `initialized` notification. A binary that exists but crashes on first real use, or speaks an incompatible protocol version, fails this check the same way a missing binary does.
3. **Atomic swap.** Only once verification passes, point the "active" reference at the new candidate using an operation that is atomic on the filesystem, a symlink `rename` over the existing "current" pointer, for instance. `rename` on the same filesystem either fully succeeds or doesn't happen at all; there's no window where a concurrent reader sees a half-updated pointer. If staging or verification fails at any point, the previous "active" version is simply never touched, so a bad update degrades to "the same version stays active and a warning is logged," never to "nothing works."

This pattern generalizes well beyond MCP servers: any dependency that a long-running agent session or automated startup process pulls in at runtime (plugins, extensions, language-server binaries) benefits from the same shape. It also composes naturally with a release-age gate: hold back a candidate until its publish timestamp has aged past some minimum threshold, and treat "can't confirm the age" as equivalent to "too young" rather than as a pass. That closes the gap where a just-published, compromised release would otherwise sail through pure integrity-hash pinning the moment the pin is bumped.

A less obvious but load-bearing detail: the "verify" step should be strict enough to fail the whole startup sequence loudly if it can't run at all, rather than degrading silently to a warning. An agent session that starts with a critical tool silently unavailable is a worse failure mode than a container that refuses to start until the tool is confirmed working.

## The version-skew trap: don't trust a bundled resolver, trust what's actually installed

A specific and easy-to-hit variant of "the tool works on my machine but not in this container": an MCP server package that bundles its own copy of a browser-automation or runtime-discovery library (a vendored, possibly alpha-track, browser driver, for example) will often try to resolve its own idea of which binary to launch, which can silently diverge from whatever browser binary the rest of the project's tooling actually has installed and pinned. A `--browser <name>` style flag on such a tool may not even mean "the plain build of that browser" either; it can map to a differently-branded distribution channel the project never installed at all.

The reliable fix is to stop trusting the bundled resolver's guesswork entirely: scan the actual cache directory where the project's own tooling installs its browser binaries, find the highest available revision that matches the expected binary path shape, and pass it explicitly via whatever "use exactly this executable" flag the MCP server exposes. This sidesteps the resolution logic completely rather than trying to keep two independently-versioned resolvers in sync.

## Tool listing works without an approval bypass; invocation doesn't

When verifying MCP wiring inside a non-interactive, no-TTY automation context (a CI job, a scripted health check, a `--print`/`exec`-style one-shot CLI invocation), expect a split: **listing** which tools a connected MCP server registers typically works without any special approval flag, while **invoking** one of those tools is commonly gated behind an interactive-approval step that a non-interactive session can't satisfy by default. Some CLIs deny the call silently in that case; others require an explicit "bypass approvals" flag or a pre-established trust configuration.

For automated health checking, this is good news: confirming that a server is reachable and its tools are registered (the wiring is correct) does not require reaching for an approval-bypass flag at all. Reserve those bypass flags for a deliberate, one-off manual verification, not for anything baked into routine automation, since they typically also bypass other safety gates (sandboxing, exec policy) at the same time.

## Where each of the big three agentic CLIs reads MCP config from, and what surprised us

This is the most reusable finding: three popular agentic coding CLIs, each with MCP support, each read their MCP server configuration from a different location, and their trust/auto-detection behavior does not generalize from one to the next. Verify each of these empirically for the specific CLI versions in use; documented behavior and observed behavior diverged more than once during this investigation.

| CLI | Typical MCP config location | What surprised us |
|---|---|---|
| Claude Code | A project-root config file (for example `.mcp.json`), auto-detected by current working directory | Works with no extra step once the file is in place and the CLI is launched from within the project; no explicit "activate this project" call needed. |
| Antigravity-style CLI | A project-specific config path (for example under an `.agents/` directory in the project root) | A non-interactive, single-shot invocation mode (a `--print`-style flag) did **not** auto-detect the current directory as a project in our testing; the workspace config was only read once an explicit project context was established (an explicit "new project" or "use this project id" flag). Interactive use of the same CLI is expected to auto-detect by working directory the way Claude Code does, but that difference between interactive and non-interactive resolution is easy to miss if you only test one mode. |
| Codex-style CLI | A project-root TOML config file (for example `.codex/config.toml`), merged with a global user-level config | A per-project "trust level" setting, which does gate other project-local features (hook execution, exec-policy rule files), turned out **not** to gate whether MCP server configuration gets loaded at all. We confirmed this directly: a worktree with no trust entry whatsoever for its path still had its MCP servers listed and available. Don't assume an untrusted-project setting silently disables MCP wiring for this style of CLI; check directly with that CLI's own "list configured MCP servers" or doctor-style diagnostic command. |

The general lesson, independent of which three CLIs you're actually integrating: **never assume config-location or trust-scoping parity across agentic CLIs, even ones that otherwise look similar on the surface.** Confirm each one's actual behavior with its own diagnostic commands (a "list configured servers" command, a "list registered tools" call in non-interactive mode) rather than inferring it from another CLI's conventions or from documentation alone.
