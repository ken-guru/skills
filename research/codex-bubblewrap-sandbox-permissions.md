# Codex/Bubblewrap sandbox permissions in `templates/codex/compose-fragment.yml`

Research for [ken-guru/skills#212](https://github.com/ken-guru/skills/issues/212). Feeds a downstream decision on whether to narrow the container runtime grant in `/workspace/skills/setup-devcontainer/templates/codex/compose-fragment.yml`:

```yaml
cap_add:
  - SYS_ADMIN
security_opt:
  - seccomp=unconfined
  - systempaths=unconfined
```

This is research only — no files other than this one were modified.

## 1. Codex CLI's own sandbox documentation

**Primary sources checked:** `developers.openai.com/codex/cli` (permanently redirects, HTTP 308, to `learn.chatgpt.com/docs/sandboxing`); `github.com/openai/codex` (public repo, confirmed reachable via unauthenticated `gh api`), specifically `codex-rs/linux-sandbox/README.md` and the vendored `codex-rs/vendor/bubblewrap/` source tree.

**Findings:**

- Codex's Linux sandbox does use Bubblewrap as its primary/default mechanism, with Landlock kept only as an explicit legacy fallback (`use_legacy_landlock = true`). Direct quote, `codex-rs/linux-sandbox/README.md` lines 24–26: "Bubblewrap is the default filesystem sandbox... Legacy Landlock + mount protections remain available as an explicit legacy fallback path." Codex prefers a system `bwrap` on `PATH`, and falls back to a bundled `codex-resources/bwrap` binary "which requires support for unprivileged user namespace creation" if none is found (lines 10–16).
- Codex explicitly unshares the user namespace and PID namespace: "the helper explicitly isolates the user namespace via `--unshare-user` and the PID namespace via `--unshare-pid`" (README lines 84–85), and unshares the network namespace when network is restricted (lines 86–90).
- Codex is aware of running inside containers already: "it mounts a fresh `/proc` via `--proc /proc` by default, but you can skip this in restrictive container environments with `--no-proc`" (README lines 93–94). This is Codex's own escape hatch for exactly the kind of masked-`/proc`-path problem that motivates `systempaths=unconfined` (see §3 and §4) — it is not exercised by the current compose fragment, which does not pass `--no-proc`.
- `learn.chatgpt.com/docs/sandboxing` (the current canonical Codex sandboxing doc, reached via the 308 redirect from `developers.openai.com/codex/cli`) documents installing a system `bubblewrap` package and, specifically for **Ubuntu 24.04 and 25.04**, a host-level AppArmor restriction on unprivileged user namespaces, recommending either loading a `bwrap-userns-restrict` AppArmor profile (`apparmor_parser -r /etc/apparmor.d/bwrap-userns-restrict`) or, as a fallback, `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0`.
- **This doc does not address Docker/devcontainer nesting at all.** It has no guidance on what container capabilities, seccomp profile, or AppArmor settings are needed to run Codex's bubblewrap sandbox inside an already-containerized environment such as Docker. OpenAI does not document container-in-container requirements for Codex.
- No `.devcontainer/` directory or Docker Compose file exists anywhere in `openai/codex` (`git ls-tree -r` over the full repo tree, checked directly), so there is no first-party example of OpenAI running Codex's own bubblewrap sandbox inside Docker to compare against.

**Confidence:** High confidence that bubblewrap is confirmed as the current mechanism (direct, current, first-party source). High confidence that OpenAI's docs are silent on Docker-nesting permissions — this is an explicit absence, not a gap in my search.

## 2. Bubblewrap upstream's own documentation/source on minimum privilege

**Primary sources checked:** `github.com/containers/bubblewrap` (canonical location — no org move found; `containers/bubblewrap` is current and active) `README.md` and `bubblewrap.c`; the identical vendored copy inside `openai/codex` at `codex-rs/vendor/bubblewrap/bubblewrap.c` (used to get exact line numbers for what Codex actually ships/builds); `man7.org/linux/man-pages/man7/user_namespaces.7.html`.

### 2a. Does creating an unprivileged user namespace require CAP_SYS_ADMIN?

**No — not at the kernel level, and not in bubblewrap's own default (non-setuid) build.**

- `user_namespaces(7)` (man7.org): "Since Linux 3.8, unprivileged processes can create user namespaces... the other types of namespaces can be created with just the CAP_SYS_ADMIN capability in the caller's user namespace." I.e. `CLONE_NEWUSER` itself needs no capability; it is namespace types *other than* the user namespace (mount, PID, net, UTS, IPC, cgroup) that need `CAP_SYS_ADMIN` **in the caller's own user namespace** — and a process that has just unshared into a brand-new user namespace automatically holds full capabilities, including `CAP_SYS_ADMIN`, *within that new namespace*, at zero cost to the outer process. This is exactly the "container features for unprivileged users" trick bubblewrap is built on.
- `containers/bubblewrap` `README.md`: "There is a feature in the Linux kernel called user namespaces which allows unprivileged users to use container features. Bubblewrap uses these to build the sandbox, allowing any user to use the tool" and "Historically, bubblewrap also supported a setuid mode for systems where unprivileged user namespaces were not supported. However, this has been removed" (lines 14–21).
- `bubblewrap.c` (vendored in `openai/codex` at `codex-rs/vendor/bubblewrap/bubblewrap.c`, identical logic to upstream `containers/bubblewrap`):
  - Line 61: `#define is_privileged 0` — when built *without* `-Dsupport_setuid=true` (the packaging bubblewrap's own `SECURITY.md` calls "the recommended way to package bubblewrap" since 0.11.2), `is_privileged` is a compile-time constant `0`.
  - Lines 685–687: `REQUIRED_CAPS_0` (`CAP_SYS_ADMIN | CAP_SYS_CHROOT | CAP_NET_ADMIN | CAP_SETUID | CAP_SETGID | CAP_SYS_PTRACE`) is only ever consulted inside `set_required_caps()`, which is only called from the `acquire_privs()` branch guarded by `#ifdef ENABLE_SUPPORT_SETUID` (lines 849–886) — i.e. **only in the legacy setuid-root binary mode that upstream has disabled by default.**
  - The comment directly above `acquire_privs()` (lines 830–834) states plainly: *"If bwrap is not setuid, then this does nothing, and it relies on unprivileged user namespaces to be used."*
  - `README.md` line 200's statement that bubblewrap "retain[s] only a few specific Linux capabilities such as `CAP_SYS_ADMIN`" is describing that same legacy setuid-mode design (in a paragraph contrasting bubblewrap's setuid model with Firejail's), not a runtime requirement of the modern unprivileged build.

So: **bubblewrap itself, as vendored and built by Codex, does not need the calling process (i.e. the Docker container) to hold `CAP_SYS_ADMIN`.** It needs `unshare(CLONE_NEWUSER)` to succeed (no capability required by the kernel), after which it has `CAP_SYS_ADMIN` for free inside its own new namespace for the subsequent mount/pivot_root/chroot work.

**Why `cap_add: SYS_ADMIN` is in the compose fragment anyway — this is the crux, and it's a Docker seccomp policy artifact, not a bubblewrap/kernel requirement.** I fetched Docker's actual default seccomp profile (`moby/profiles`, `seccomp/default.json` — this is the file Docker Engine vendors and applies by default; confirmed via `moby/moby`'s own vendor tree) and found the exact rule:

```json
{
  "names": ["bpf","clone","clone3","...","mount","mount_setattr","...","setns","...","umount","umount2","unshare"],
  "action": "SCMP_ACT_ALLOW",
  "includes": {"caps": ["CAP_SYS_ADMIN"]}
}
```
plus a narrower fallback rule that allows plain `clone()` (no `CLONE_NEW*` flags — decoded mask `0x7E020000` = `CLONE_NEWNS|CLONE_NEWCGROUP|CLONE_NEWUTS|CLONE_NEWIPC|CLONE_NEWUSER|CLONE_NEWPID|CLONE_NEWNET`) even without `CAP_SYS_ADMIN`, and a rule that unconditionally `SCMP_ACT_ERRNO`s `clone3` (`errno 38`, `ENOSYS`) when the caller lacks `CAP_SYS_ADMIN` — with **no** narrower allowance for `clone3` at all in that case.

Docker computes this "`includes`/`excludes`: `caps`" gating **once, at container-creation time**, from the capability set the container was started with (via `--cap-add`/`cap_add`) — it is not a live/dynamic capability check inside the BPF program. This is corroborated by `moby/moby#43086` ("Cannot unshare without CAP_SYS_ADMIN, despite `/proc/sys/kernel/unprivileged_userns_clone`"), where a maintainer-adjacent thread confirms `docker run --security-opt apparmor:unconfined ubuntu unshare -U` fails with "Operation not permitted" and only succeeds once `--cap-add SYS_ADMIN` is added — even though the kernel itself permits unprivileged `unshare(CLONE_NEWUSER)`. `moby/moby#42441` ("Reevaluate the default seccomp policy on clone and unshare") makes the same point explicitly: Docker's policy is *more restrictive than the kernel*, blocking `CLONE_NEWUSER` for `clone`/`unshare` unless `CAP_SYS_ADMIN` is present, "even though the kernel has permitted this since Linux 3.8." This is a deliberate Docker default-seccomp-profile design choice, not a kernel or bubblewrap constraint.

**Net assessment for `cap_add: SYS_ADMIN`:** granting it is **not required by bubblewrap or the kernel's actual permission model** for unprivileged-userns sandboxing — it is currently required only as a side-effect of how Docker's default seccomp profile is gated (by capability grant at container-creation time, not by what the process really needs at syscall time). A seccomp policy that separately allowlists the specific `clone`/`clone3`/`unshare`/`mount`/`pivot_root` calls bubblewrap needs (see §2b) — without the `caps: [CAP_SYS_ADMIN]` gate — would, per this same source material, remove the *only* documented reason `cap_add: SYS_ADMIN` is needed today. **No primary source shows this has actually been done and tested for bubblewrap specifically**, so this is reasoning from primary sources, not a confirmed working configuration.

### 2b. Would a narrow, custom seccomp profile work instead of `seccomp=unconfined`?

- Docker's default profile (`moby/profiles/seccomp/default.json`) blocks, for containers without `CAP_SYS_ADMIN`: `mount`, `umount`/`umount2`, `pivot_root` (blocked unconditionally elsewhere in the same profile — not shown in the `clone`/`unshare` group above but present as its own `SCMP_ACT_ERRNO` entries), `setns`, and namespace-creating `clone`/`unshare`/`clone3` calls. A profile derived from Docker's default that (a) drops the `caps: [CAP_SYS_ADMIN]` gate specifically for the `clone`/`clone3`/`unshare` rule (or narrows its argument mask to just `CLONE_NEWUSER|CLONE_NEWNS|CLONE_NEWPID|CLONE_NEWUTS|CLONE_NEWIPC` — the flags Codex's bwrap invocation actually uses per §1) and (b) unconditionally allows `mount`/`pivot_root`/`setns`/`umount2` is, by the kernel-capability reasoning in §2a, plausible: once bwrap is inside its own new user+mount namespace it holds real, kernel-enforced `CAP_SYS_ADMIN` there regardless of what the outer container was granted, so a seccomp filter that simply lets the syscalls *through* (rather than gating them on the outer container's capability set) should be sufficient at the kernel level.
- **I did not find a primary source (OpenAI, bubblewrap upstream, or Docker) that has actually published such a minimal bubblewrap-in-Docker seccomp profile.** The closest thing that exists and is documented working is **not minimal**: it's swapping Docker's default profile for Podman's much larger default profile (`containers/common`'s `pkg/seccomp/seccomp.json`), which is broadly more permissive and allows `unshare` — see §4 for the direct evidence this was used successfully with Docker for "at least some bwrap commands."
- **Grading this (b) vs (c):** no source shows a hand-built *minimal* profile working — the one narrower-than-`unconfined` alternative that's confirmed working (Podman's profile) is a large, general-purpose superset in its own right, not a scoped allowlist. So a bespoke minimal profile is **(c) plausible-but-untested**, while "swap in Podman's `seccomp.json`" is closer to **(b)** — a specific, named, narrower-than-`unconfined` alternative with direct (if informal) evidence of working, short of a purpose-built minimal profile.

## 3. `security_opt: systempaths=unconfined`

**What it actually is, per primary source (not purely an AppArmor mechanism):** I traced `systempaths=unconfined` to its origin. `moby/moby` issue **#36597** ("[proposal]: option to not mask or set read-only paths in /proc") proposed it explicitly for "nesting user-namespaced rootless containers inside a Docker container without setting `--privileged`" — i.e. this exact bubblewrap-style use case. The implementing PR, **`moby/moby#36644`**, adds `MaskedPaths []string` / `ReadonlyPaths []string` fields directly to `HostConfig` (`api/types/container/host_config.go`) and, in `daemon/oci_linux.go`, sets `s.Linux.MaskedPaths` / `s.Linux.ReadonlyPaths` directly on the **OCI runtime spec** passed to the container runtime (runc) — this is enforced by the OCI runtime via bind-mounting `/dev/null` (or read-only remounts) over specific `/proc` and `/sys` paths, **independent of any LSM (AppArmor/SELinux)**. `docker/cli` PR **#1808** adds the client-side `--security-opt systempaths=unconfined` flag, which a reviewer comment there confirms "is handled client-side" by sending empty `MaskedPaths`/`ReadonlyPaths` arrays — it does not touch the AppArmor profile selection at all. Docker's own CLI reference (`docs.docker.com`) describes it simply as "Turn off confinement for system paths (masked paths, read-only paths) for the container," with no AppArmor-specific language.

**Implication for the AppArmor-enabled-hosts question:** because masking is enforced by the OCI runtime's mount setup rather than by an AppArmor policy, `systempaths=unconfined` does something (removes the `/proc`/`/sys` masks) on **any** Docker host, including ones without AppArmor enabled at all (e.g. non-Debian/Ubuntu hosts) — it is not a no-op off AppArmor-enabled distros. The premise in the research prompt that this is fundamentally an AppArmor option turns out to be imprecise: it's an OCI masked-/readonly-paths setting that Docker happens to expose via `--security-opt`, alongside (but mechanically separate from) `--security-opt apparmor=...`.

**Is it necessary, separable from the seccomp change, or redundant?** Primary-source community evidence (§4, `containers/bubblewrap#505`, comment by `iTrooz`) shows it addressing a *real, distinct* failure mode: bubblewrap's `--unshare-pid` + `--proc <dir>` remount of `/proc` fails with "Operation not permitted" specifically because of a kernel behavior around remounting over an already-masked `/proc` path (cites a kernel mailing-list commit); the fix there was Podman's `--security-opt unmask=ALL` (Podman's name for the same OCI masked-paths mechanism Docker calls `systempaths=unconfined`). This is a different failure than the seccomp-blocked-syscall failure `seccomp=unconfined` fixes — **the two settings are not redundant with each other**; they address independent restriction layers (seccomp syscall filtering vs. OCI path masking). Codex's own `--proc /proc` behavior (§1, README lines 93–94) is exactly the kind of remount this setting is protecting; Codex does expose a `--no-proc` flag that Codex itself doesn't currently pass in this compose fragment's usage, so a narrower alternative to `systempaths=unconfined` may exist at the *Codex* config layer rather than the *container* layer, but that is outside this compose fragment's control and is speculative — no primary source confirms `--no-proc` alone eliminates the need for `systempaths=unconfined` in practice.

**Important gap noticed while researching this:** the current compose fragment sets `seccomp=unconfined` and `systempaths=unconfined`, but **not** `security_opt: apparmor=unconfined`. Multiple primary-source reports in §4 (`thelamer`, `mulawamichal` on `containers/bubblewrap#505`) needed `apparmor=unconfined` *in addition to* the seccomp and capability changes to get bubblewrap working in their Docker containers. Whether the current fragment works without it (perhaps because `systempaths=unconfined` happens to relax enough of what Docker's own `docker-default` AppArmor profile would otherwise also restrict, or because the target base images run without AppArmor enforced) is not established by any source I found — it's worth flagging to whoever owns the downstream decision as an open question about whether the *existing* three-setting grant is even known-sufficient, separately from whether it's over-broad.

## 4. Prior art

- **`containers/bubblewrap` issue #505** ("bubblewrap inside unprivileged docker") is the single richest piece of prior art found, and is itself a primary source (the bubblewrap maintainer `smcv` participates directly). Key data points, all directly quoted from the issue:
  - The reporter tried granting **every** Linux capability (not just `SYS_ADMIN`) with Docker's **default** seccomp/AppArmor still in place, and it still failed (`bwrap: Failed to make / slave: Permission denied`) — capabilities alone, even a full set, are not sufficient.
  - `thelamer`: "You are missing apparmor: `--security-opt apparmor=unconfined`."
  - `s-hamann`: "You are also missing the seccomp filter: `--security-opt seccomp=unconfined`. Docker's default seccomp filter blocks the `clone` and `unshare` syscalls (among others), which bubblewrap needs to create a new namespace. Podman's seccomp filter is more permissive. Bubblewrap works (with a few limitations) in an unprivileged Podman container."
  - `mulawamichal` reports the working combination as `--cap-add SYS_ADMIN --security-opt apparmor=unconfined --security-opt seccomp=unconfined` — i.e. **broader** than the current compose fragment (it also unconfines AppArmor).
  - Bubblewrap maintainer `smcv`: *"bubblewrap cannot work if it's run inside a container that doesn't allow the necessary syscalls, mount operations, etc... The precise permissions that are required are not obvious, partly because the kernel gives us very little diagnostic information when we don't have them ('Permission denied' is as much as we get). This isn't a bubblewrap bug: doing impossible things is out-of-scope for this project."* — a direct, first-party statement that upstream bubblewrap has not characterized (and does not intend to characterize) a minimal container permission set.
  - `andrew-aladjev` / `smcv`: on Ubuntu 24.04+, there is a *separate* host-kernel AppArmor restriction (`kernel.apparmor_restrict_unprivileged_userns`) blocking unprivileged user-namespace creation unless the calling binary has an AppArmor profile with the `userns` permission; Ubuntu's stated position (linked Launchpad bug) is that they will not add a generic profile for `bwrap` itself, only for specific known callers (Flatpak, Steam, etc.) — Codex is not among them, and this compose fragment's target (a devcontainer, likely on Ubuntu 22.04 per GitHub Codespaces' current stable host image, or a user's own Docker host) may or may not carry this specific kernel patch.
  - `congwang-mk` names an alternative sandboxing tool, `sandlock` (Landlock + seccomp, no namespaces), that works in unprivileged Docker/Kubernetes **without** `SYS_ADMIN`, AppArmor, or seccomp overrides — not applicable here since Codex specifically uses bubblewrap (§1), not Landlock-only, as its default, but relevant as evidence that namespace-free sandboxing avoids this whole problem class.
  - **`exyi`**: *"I didn't want to set seccomp to completely unconstrained, but it is possible take the Podman seccomp profile and use it with Docker... Podman allows unshare, so at least some bwrap commands will work."* (links `containers/common`'s `pkg/seccomp/seccomp.json`.) This is the one piece of prior art showing a **named, narrower-than-`unconfined` seccomp profile actually used successfully with Docker for bubblewrap** — though it is itself a large, general-purpose profile (not purpose-built for bubblewrap) and the reporter caveats "at least some bwrap commands will work," not full success.
  - `iTrooz`: hit a *different* failure (`bwrap: Can't mount proc on /newroot/proc: Operation not permitted`) caused specifically by masked-path interaction with `/proc` remounting, fixed by Podman's `--security-opt unmask=ALL` — Docker's `systempaths=unconfined` equivalent (§3).
- **`moby/moby#42441`** and **`#43086`**: confirm, from the Docker/Moby side, that Docker's own seccomp policy — not the kernel — is what forces the `CAP_SYS_ADMIN` grant for `clone`/`unshare` with `CLONE_NEWUSER`, and that this is being tracked as a possible policy change upstream (not yet resolved as of research date).
- **No prior art found of anyone running Codex CLI's specific bubblewrap-based sandbox** (as opposed to bubblewrap generically) inside a devcontainer or CI with a narrower grant than the current fragment. No blog posts or discussions specifically about Codex-in-Docker permissions were found.

## Verdicts

| Setting | Verdict | Justification |
|---|---|---|
| `cap_add: SYS_ADMIN` | **(c) Plausible-but-untested to narrow.** Not literally proven-safe-to-drop as a superset, but strong primary-source reasoning (kernel `user_namespaces(7)`; bubblewrap's own vendored source showing `CAP_SYS_ADMIN` is only consulted in the disabled-by-default setuid code path) shows the capability is not actually needed by bubblewrap or the kernel for the unprivileged-userns path — it is only needed today to satisfy Docker's default seccomp profile's capability-gated `clone`/`unshare`/`mount` rules (`moby/profiles/seccomp/default.json`; corroborated by `moby/moby#42441`, `#43086`). Narrowing it would require *also* replacing the seccomp policy (it can't be dropped alone — `containers/bubblewrap#505`'s reporter granted every capability, unmodified seccomp, and still failed), so it is not an independently-safe change and needs empirical testing paired with a seccomp change. |
| `security_opt: seccomp=unconfined` | **(c) Plausible-but-untested to narrow.** Docker's own default profile's exact blocking rules are now identified precisely (§2b): `clone`/`clone3`/`unshare`/`mount`/`umount2`/`setns`/etc. gated behind `CAP_SYS_ADMIN` at container-creation time. A scoped custom profile that allowlists just these calls (ideally restricted to the specific `CLONE_NEW*` flag combination Codex's bwrap invocation uses) is reasoned to be sufficient by the kernel-capability model in §2a, but no primary source has published or confirmed such a minimal profile working for bubblewrap-in-Docker. The one confirmed narrower-than-`unconfined` alternative in the wild — swapping in Podman's full default seccomp profile (`containers/common/pkg/seccomp/seccomp.json`) — is itself a broad superset, reported by a single community member (`exyi`, `containers/bubblewrap#505`) as making "at least some" bwrap commands work, not a scoped minimal allowlist and not exhaustively verified. |
| `security_opt: systempaths=unconfined` | **(c) Plausible-but-untested to narrow, with a caveat: it is not redundant with the seccomp setting and does something on any Docker host regardless of AppArmor.** Traced to its exact mechanism in `moby/moby` source (`daemon/oci_linux.go` setting OCI `Linux.MaskedPaths`/`ReadonlyPaths` directly) — it is an OCI-runtime path-masking control, not an AppArmor-gated one, so it is *not* a no-op on non-AppArmor hosts as the research prompt's framing suggested. It addresses a distinct, real failure mode (bubblewrap's `/proc` remount under `--unshare-pid`, per `containers/bubblewrap#505`'s `iTrooz` comment) separate from what seccom­p fixes. A narrower alternative — passing a specific, smaller `MaskedPaths`/`ReadonlyPaths` override, or having Codex pass `--no-proc` (which Codex's own README documents as an option for "restrictive container environments," `codex-rs/linux-sandbox/README.md` lines 93–94) instead of remounting `/proc` — is plausible but unconfirmed by any primary source for this exact use case. |

No setting reached grade **(a)** — no primary source states any of these three exact settings, as configured in this compose fragment, is the *required, minimum* form for this use case. No setting reached grade **(b)** in the strict sense of "a specific named narrower alternative with primary-source evidence it works" for a *minimal, purpose-built* replacement; the closest thing to (b) is the Podman-seccomp-profile substitution for `seccomp=unconfined`, which is narrower than `unconfined` and has direct (if informal, single-reporter, partial-success) evidence behind it.

## Bottom line for the downstream decision

The inline comment's claim that this is "the minimum" is not supported by primary sources — the opposite is closer to true: kernel and bubblewrap-source evidence indicates `CAP_SYS_ADMIN` is not actually required by bubblewrap's unprivileged (non-setuid) mode, and it, along with `seccomp=unconfined`, exists mainly to satisfy Docker's default seccomp profile's capability-gated syscall rules, which are demonstrably narrower than what the kernel itself permits. That said, nobody — not OpenAI, not bubblewrap upstream, not the Docker/Moby maintainers, and not any community report found — has published a confirmed *minimal* working alternative for this exact scenario (Codex's bubblewrap sandbox inside Docker); the one documented narrower-than-`unconfined` seccomp substitute (Podman's profile) is itself broad and only reported as partially working. `systempaths=unconfined` is confirmed to do something real and distinct from the seccomp setting on any Docker host (it's OCI-level, not AppArmor-gated), and should not be assumed removable without addressing the `/proc`-masking failure mode it exists for. Before narrowing any of these three settings in production, the concrete next step is empirical: build a custom seccomp profile derived from Docker's default that allowlists exactly the syscalls/flag-combinations bubblewrap's Codex invocation uses (per §1's documented `--unshare-user`/`--unshare-pid`/`--proc` usage) without the `CAP_SYS_ADMIN` gate, drop `cap_add: SYS_ADMIN`, and test it against Codex's actual sandboxed command set in this repo's own CI — as well as re-testing whether `systempaths=unconfined` can be replaced by Codex's own `--no-proc` flag — before adopting any narrower grant.
