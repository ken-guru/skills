# Build-time network access vs. runtime-firewalled network access

If your devcontainer runs an outbound firewall (an allowlist of known-good domains, applied by a script that runs on container start), that firewall does not exist yet during the image build, and it does not exist yet during whatever setup step runs before the firewall script itself executes. This gives every setup step exactly two safe places to reach the open internet from: build time, before the firewall is even a concept, or runtime, after the firewall exists, with the exact destination host added to its allowlist first. There is no safe third option where a step "temporarily" bypasses the firewall or races it.

Treat this as load-bearing, not a style preference. The classic way to discover it the hard way: install your firewall's own dependencies (the packages that let it manage netfilter rules at all) via a runtime package-manager call in your setup script. The first time the firewall starts enforcing on every container start, that same package-manager call starts failing, because the firewall it depends on existing has now blocked the package mirror it needs to reach. The fix is not a firewall exception for the mirror; it's moving that install into the image build, a phase with no firewall at all. Any step that needs broad, unpredictable network access, an OS package mirror, a browser-automation vendor's binary CDN, a CLI's release-asset host, belongs at build time or in the earliest runtime setup step, never in a step that runs after the firewall initializes, unless its destination is explicitly allowlisted first.

A related trap: don't assume a floating base-image tag is safe just because it resolves at build time. If you pin your image to a moving target (a distribution's "latest" alias rather than a specific release codename), the tag can drift out from under you between rebuilds, and some of your vendored tooling may not have caught up. A concrete version of this: a browser-automation framework's browser-binary distribution can lag a brand-new OS codename by months, publishing builds for the prior codename only, on some architectures. If your base image floats past that boundary, an install step that worked yesterday fails today with no code change on your side. Pin to the exact codename you've verified against your dependencies' own release matrices, and re-verify that matrix deliberately when you choose to move the pin, rather than letting it move on its own.

One more instance of the same instinct, in a smaller and easier-to-miss form: keep a general-purpose scripting runtime installed even if nothing in your own repository's scripts calls it, when the container's real users include an AI coding agent that reaches for a quick inline script mid-session. A dependency audit that only greps your own scripts for usage will miss this consumer entirely, because its usage is by design never committed anywhere. Document the reasoning inline where the package is installed, so the next audit doesn't remove it for looking unused.

# Capability scoping for nested sandboxing

If a tool running inside your devcontainer needs its own nested sandbox (a namespace-based process isolation tool, for instance), it will typically need one or two specific Linux capabilities and a relaxed seccomp or filesystem-path profile, not full container privilege. Reach for `privileged: true` and you grant every capability and device the kernel has, not just the two or three the nested sandbox actually touches; reach for the narrow grant instead and the blast radius of a compromised nested process stays bounded to what you explicitly named.

Two closely related patterns show up together often enough to name separately: a firewall running inside the container needs `NET_ADMIN` and `NET_RAW` to manage its own netfilter rules, while a nested process-sandboxing tool typically needs `SYS_ADMIN` plus an unconfined seccomp profile and unconfined system paths, because creating a user namespace and then mounting a private filesystem tree inside it is a privileged operation that some container runtimes (notably ones running on top of a lightweight Linux VM rather than bare-metal Linux) can't satisfy through the usual AppArmor escape hatch. Grant exactly those, comment each one inline with which nested tool needs it and why, and add a startup health check that actually exercises the nested sandbox (create the namespace, mount, pivot root) rather than just checking the binary exists, so a capability regression surfaces immediately as a clear failure instead of a confusing error buried in whatever the nested tool was trying to do.

# Named-volume ownership: two different gotchas that look like the same bug

Following this skill's own recommendation to give a non-root user's tool config, SSH keys, and shell history each their own named volume produces a permission error the very first time a tool tries to write there, unless one extra fact is accounted for: a named volume's first mount copies ownership from whatever already exists at that exact path in the image. If nothing exists there, Docker creates the path as root on first mount, regardless of which user the container otherwise runs as. The symptom is usually indirect: a CLI crashing with `EACCES` trying to write its own project registry or config file on first run, which reads like a tool bug until you check who owns the mount point.

The fix depends on *where* the volume is mounted, and conflating the two cases is the actual trap:

- **A named volume mounted directly under the non-root user's home directory** (tool config, SSH keys, shell history) can be fixed entirely at build time: `mkdir` the exact path and `chown` it to that user in the Dockerfile, before the image is done building. [`Dockerfile.skeleton`](templates/build/Dockerfile.skeleton) does this as part of creating the non-root user, and [`docker-compose.skeleton.yml`](templates/build/docker-compose.skeleton.yml)'s named-volume block calls out which paths need a matching entry there.
- **A named volume nested *inside* the workspace bind mount** (a build-output or dependency-cache directory mounted at some path under `/workspace`, for caching something like a compiled-language build directory across rebuilds) is a fundamentally different case, and the build-time fix above does not apply to it. Because the workspace itself is a bind mount from the host, Docker resolves the nested volume's first-mount ownership against the live host directory at container *start*, not against anything baked into the image at build time. No Dockerfile change can fix this; the chown has to happen at runtime, in a postCreate/postStart hook, after both mounts are already live. The more robust option is usually to avoid the nesting entirely: point the build tool at a cache directory outside `/workspace` via whatever "override the build-output location" mechanism it exposes, which sidesteps the ownership question altogether instead of working around it.

Treat these as two separate gotchas, not one. The fix for the first one applied to the second one will build successfully and then fail with a permission error the first time the tool actually tries to write to the nested path, which is exactly the kind of thing that looks like the same bug recurring when it's actually a different bug with a different fix.

# npm global installs as a non-root user need their own prefix

`npm install -g` as the container's non-root user fails immediately with `EACCES` the first time it runs, because the default global-install prefix on most base images (typically under `/usr/lib/node_modules`) is writable only by root. This is easy to hit specifically when installing an agentic CLI's own binary globally inside the container, since that's a very likely companion step whenever a devcontainer wires up agentic tooling at all -- a different case from the scoped `--prefix` staging installs an MCP-server install pipeline uses (see [MCP-MULTI-CLI-WIRING.md](MCP-MULTI-CLI-WIRING.md)). Set `NPM_CONFIG_PREFIX` to a directory under the non-root user's home directory, and add that directory's `bin` subdirectory to `PATH`, before any global npm install happens, whether that install runs later in the same Dockerfile or in a runtime setup hook.

# A Debian-family base image silently resets `ENV PATH` for login shells

`ENV PATH` additions in a Dockerfile reach non-login, non-interactive shell invocations (an ordinary `docker exec ... bash -c "..."`) reliably, but Debian and Ubuntu base images set `PATH` unconditionally for non-root users in `/etc/profile`, with no check for a value the environment already set, which silently overwrites whatever the image's own `ENV PATH` contributed the moment anything invokes a login shell (`bash -l`, and some terminal or IDE integrations that launch login shells by default). This is a base-image-specific behavior, not universal across every Linux distribution, but Debian and Ubuntu are extremely common devcontainer bases, and it's easy to miss entirely if your own testing only ever used `docker exec`, which never triggers it.

The reliable fix is to stop relying on `ENV PATH` alone and also write the same additions to a script under `/etc/profile.d/`, which both login and most interactive non-login shells source. This is a one-line addition anywhere `ENV PATH` is extended for the non-root user's own tooling, and it's worth doing on every such addition, not just the first one you happen to hit the bug on.
