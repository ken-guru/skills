# Antigravity CLI's `--sandbox` flag: what it restricts, how it's implemented, and whether it needs anything from a host container

Research for [ken-guru/skills#284](https://github.com/ken-guru/skills/issues/284), a child of the wayfinder map issue [#281](https://github.com/ken-guru/skills/issues/281) ("Decide setup-devcontainer's hardening priorities"). Feeds a downstream decision on whether `setup-devcontainer` should add a Shared-Container-level network/filesystem baseline, and how `setup-antigravity-devcontainer`'s current design (no `--sandbox` in its YOLO alias, no Capability Seam grant) should relate to that baseline.

This is research only — no files other than this one were modified.

---

## 1. What `--sandbox` restricts, per Antigravity's own docs

**Primary sources checked directly:** `antigravity.google/docs/cli/sandbox/` (the page named in the issue), `antigravity.google/docs/cli/permissions`, `antigravity.google/docs/cli/settings`, `antigravity.google/docs/cli/features/`, and `antigravity.google/docs/sandbox` (a distinct, more marketing-oriented overview page linked from the CLI sandbox page's "See also").

**Filesystem:** the sandbox mounts the workspace and temp/build-cache directories read-write, mounts system directories such as `/usr` and `/etc` read-only, and blocks specific sensitive paths — the docs name `~/.ssh` and `.env` explicitly. Direct quote (`/docs/cli/sandbox/`): "Sensitive files like `~/.ssh` and `.env` are blocked, anything not explicitly mounted is invisible inside the sandbox." Fine-grained mount scope is driven by the `permissions` config's `write_file` (read-write mount) and `read_file` (read-only mount) rules — confirmed on `/docs/cli/permissions`, which also documents "Write implies Read."

**Network:** default-deny. Direct quote: "Sandboxed commands run without network access by default." Domains named in `read_url` permission rules are added to an allowlist.

**Process/execution:** the docs do not describe process-capability restrictions (no mention of ptrace, setuid, capability dropping, etc.) beyond the general framing that commands run "within an OS-level isolation boundary."

**Escape hatch:** an `unsandboxed(...)` permission rule (e.g. `unsandboxed(git push)`, `unsandboxed(regex:git .*)`) lets specific commands "execute outside container isolation when terminal sandboxing is enabled," without disabling the sandbox globally.

**Configuration:** `~/.gemini/antigravity-cli/settings.json` — note the path is under `~/.gemini/`, not `~/.antigravity/` (see §5 for why this repo's own skill uses a different path). Two relevant keys: `enableTerminalSandbox` (boolean) and `toolPermission` (string, e.g. `request-review`, `proceed-in-sandbox`, `strict`, `always-proceed`). The CLI flag `--sandbox` enables it for one session.

**Default value of `enableTerminalSandbox`:** the `/docs/cli/features/` page states explicitly, in a table/bullet: "**`enableTerminalSandbox`** (boolean, default: `false`)." The `/docs/cli/settings` page describes the same key's *effect* ("When enabled (`on`), restricts all agent-initiated terminal commands to a secure OS container") but does not itself restate a default value — the two pages are consistent in behavior description, and `/features/` is the one with an explicit default. **Confidence: high** that the sandbox is opt-in by default, from a direct, explicit, first-party statement.

**Confidence for this section overall: high.** All claims above are direct quotes or close paraphrases from Antigravity's own current docs pages, fetched live.

## 2. How it's implemented — and a documented-vs-observed discrepancy

**Primary source (Google's own docs):** `/docs/cli/sandbox/` states, for the two platforms it names: "Linux: Kernel namespaces isolate the filesystem, hide host processes, and cut off networking" and "macOS: `sandbox-exec` with Seatbelt profiles (SBPL) restrict filesystem access and socket connections." The Windows column is filled in only by the `/docs/cli/features/` page, which names a third mechanism: **"the CLI leverages native operating system features (`nsjail` on Linux, `sandbox-exec` on macOS, and `AppContainer` on Windows) to enforce strict containment boundaries with zero startup overhead."** This is the one place the docs name a specific tool (`nsjail`) rather than a generic "kernel namespaces" description.

**Independent, empirical, non-Google verification (GitHub issue thread, not official docs):** `google-antigravity/antigravity-cli` issue [#843](https://github.com/google-antigravity/antigravity-cli/issues/843) ("`--sandbox` is unusable on Linux: sbox aborts installing its CA certificate into a read-only `/etc/ssl/cert.pem`") contains a reporter (`istonikula`) who directly inspected the process tree and `/proc/<pid>/ns/*` namespace IDs of a running sandboxed command on 1.1.22. Their finding, quoted directly: **"no `bwrap`, `nsjail` or `sbox` process exists while a sandboxed command runs, so the 'nsjail on Linux' description in the docs does not match what 1.1.22 does."** What they found instead is a process chain `agy → exe (helper process, referenced in the report as "cf. `devtools/ai/sandbox/exebox`") → <sandboxed command>`, where the helper and the sandboxed command sit in distinct mount, network, and user namespaces from `agy` itself (namespace IDs shown differing across `mnt`/`net`/`user` between the sandboxed process and `agy`). Their summary: "Linux **constructs** an environment — separate mount, network and user namespaces via an `exe` helper. macOS **filters** the existing one in-process via Seatbelt, with the command a direct child of `agy` and no intermediary."

**How to weigh this:** the reporter's evidence is a direct, reproducible, first-hand namespace inspection (not a rumor or a guess), but it is community-sourced, not Google's own statement, and it is version-pinned (1.1.22; this repo's research date is 2026-09-14, so the implementation may have changed since). The safest reading is: Google's own docs are **internally inconsistent** about whether the Linux mechanism is literally the `nsjail` binary or a custom-built equivalent, and the one piece of direct empirical evidence found says it is **not** literally `nsjail` (no such process appears), but it **is** unambiguously a namespace-construction approach — separate mount, network, and user namespaces, built by a helper process — which is the architecturally relevant fact for this research question regardless of which specific tool or custom binary does the constructing.

**Network mechanism detail, same source:** the same reporter found the sandboxed process receives no proxy/CA environment variables (`SSL_CERT_FILE`, `HTTPS_PROXY`, `NODE_EXTRA_CA_CERTS`, `REQUESTS_CA_BUNDLE` all absent), concluding "egress appears to be blocked by the network namespace rather than intercepted" — i.e. the default-deny network posture in §1 is implemented as a genuine empty/isolated network namespace, not a MITM/allowlisting proxy, for the base "no network" case. (Separately, the sandbox does try to install a CA certificate into the sandboxed root at construction time — the cause of issue #843's actual bug — but the reporter's own testing did not establish what that installed certificate is *for*; it is plausibly related to enforcing the `read_url` domain-allowlist case rather than the default-deny case, but no primary source confirms this and it should be treated as unresolved.)

**Confidence: medium-high** that the Linux mechanism constructs mount+network+user namespaces via a helper process (direct empirical evidence, one independent reporter, version-pinned); **low** confidence on whether the underlying tool is literally `nsjail`, a fork of it, or an entirely custom binary — Google's own docs contradict themselves on this point and no primary source resolves it.

## 3. Is it self-contained, or does it assume/require Docker or a VM underneath it?

**Direct, explicit primary-source answer: it is designed to be self-contained, with no Docker or VM dependency assumed.** `/docs/sandbox` (the broader, non-CLI-specific overview page) states directly: **"there are no virtual machines or Docker images to manage and no startup delay."** `/docs/cli/features/` echoes this: "Rather than running heavy virtual machines or containers, the CLI leverages native operating system features... to enforce strict containment boundaries with zero startup overhead." This is Antigravity's own stated design goal — the sandbox is meant to run directly against the host kernel using namespaces/Seatbelt/AppContainer, not by spinning up its own container or VM layer.

**What this means for the Docker-nesting question, and what the docs do *not* say:** because the mechanism (per §2) is namespace-construction on Linux, "self-contained, no Docker required" describes what Antigravity needs to *provide* the sandbox (it doesn't need you to already have Docker running) — it says nothing about what happens when Antigravity itself is *already running inside* someone else's Docker container (a devcontainer) and tries to construct its own nested namespaces there. **No official Antigravity documentation page found addresses this nested-container scenario at all** — the same silence the sibling Codex/bubblewrap research (`research/codex-bubblewrap-sandbox-permissions.md`, branch `origin/research/codex-bubblewrap-sandbox-permissions`) found for Codex's docs. This is an explicit absence, not a gap in the search: `/docs/cli/sandbox/`, `/docs/cli/permissions`, `/docs/cli/settings`, `/docs/cli/features/`, and `/docs/sandbox` were all read in full and none mentions Docker, containers, devcontainers, `CAP_SYS_ADMIN`, seccomp, AppArmor, or nested/unprivileged user namespaces.

**Confidence: high** that self-containment (no Docker/VM dependency to *provide* the sandbox) is an explicit, stated design goal. **High confidence** that Docker-nesting compatibility is simply undocumented by Google — an absence, not ambiguity.

## 4. Does running Antigravity's sandbox nested inside a Docker container actually work? (community/empirical evidence, not official docs)

No official Google source addresses this (§3). The most direct evidence found is a third-party project's own controlled test, which is **not a primary Antigravity source** but is a first-hand, reproducible empirical report rather than speculation — treated here the same way the Codex research treated community GitHub-issue evidence: labeled clearly as such, not conflated with vendor documentation.

**Source:** `eXPerience83/remote-dev-containers` issue [#215](https://github.com/eXPerience83/remote-dev-containers/issues/215) ("docs/security: document Antigravity inner-sandbox baseline and ownership"), a project building its own hardened Docker-based dev-container tooling that also installs Antigravity CLI.

**Their reported test (2026-09-09, Antigravity CLI 1.1.27):** run inside their existing hardened Antigravity service container, with the container's Compose file, capabilities, seccomp, sysctls, and mounts **unchanged**. The container's own state showed `NoNewPrivs: 1` and two active seccomp filters. The **host kernel** had unprivileged user namespaces enabled (`kernel.unprivileged_userns_clone = 1`), but a direct in-container probe failed:

```
unshare -Ur true
unshare: unshare failed: Operation not permitted
```

Launching Antigravity with `--sandbox` started the UI, but the **first terminal tool call requested an explicit sandbox bypass**, warning the command would run outside the sandbox with full network/disk access; when the bypass was rejected and a bare `pwd` was requested instead, it failed with:

```
Encountered error in tool execution: fork/exec /root/.local/bin/agy: operation not permitted
```

**Their conclusion, quoted directly:** "Antigravity's vendor terminal sandbox is **not usable under the current hardened TrueNAS/Docker baseline** for terminal tool execution... Remote Dev must not weaken the outer security boundary (`privileged`, `SYS_ADMIN`, unconfined seccomp/AppArmor-style profiles, host namespaces, etc.) merely to make a nested vendor sandbox work." Their resulting design decision was to **not** force or manage `enableTerminalSandbox` in their supported baseline at all, and to keep the hardened outer container as the sole supported isolation boundary — declining to grant the extra container permissions a working nested sandbox would need.

**How this connects to the mechanism found in §2:** the `unshare -Ur` failure ("Operation not permitted" for creating a user namespace) is exactly the failure mode this repo's sibling Codex/bubblewrap research documented as a Docker-default-seccomp-policy artifact (Docker's default seccomp profile gates `clone`/`clone3`/`unshare`/`mount` behind `CAP_SYS_ADMIN` at container-creation time — `moby/profiles/seccomp/default.json`, corroborated by `moby/moby#42441` and `#43086`), not a kernel-level restriction (the kernel itself permits unprivileged `CLONE_NEWUSER` per `user_namespaces(7)`). Given that Antigravity's own Linux sandbox mechanism is, per §2, also namespace-construction (mount+network+user namespaces via a helper process), it is architecturally coherent that it would hit the identical Docker-seccomp-policy wall bubblewrap hits — and the TrueNAS report is direct evidence that it does, in a real hardened-container deployment.

**Caveats on this evidence:** (1) it is one project's test, on one Antigravity version (1.1.27), under a *hardened* baseline that layers extra restrictions (`NoNewPrivs: 1`, custom seccomp filters) on top of whatever Docker's own defaults are — so it doesn't cleanly isolate "does it fail under Docker's stock defaults" from "does it fail under this project's specific extra hardening"; (2) it is not a Google-published result and Google has not acknowledged this scenario in any doc found. **Confidence: medium** — a single, concrete, well-documented reproduction with exact command output, but not corroborated by a second independent source and not confirmed by the vendor.

## 5. A second, independent reason `--sandbox` is not currently a reliable safety boundary at all — even outside Docker

Two separate upstream bug reports show the sandbox failing or being defeated for reasons that have nothing to do with container nesting, which matters for weighing how much the Shared-Container baseline should be built around preserving room for it:

- **`antigravity-cli#36`** (already known to this repo — cited in `skills/setup-antigravity-devcontainer/SKILL.md` and `templates/yolo-alias-block.sh`): combining `--dangerously-skip-permissions` with `--sandbox` auto-approves the sandbox-bypass prompt along with regular permission prompts, making `--sandbox` a **no-op** whenever unattended/YOLO-style operation is used. Direct quote from the filed issue body: "the `--dangerously-skip-permissions` appears to make `--sandbox` completely ineffective... this is a pretty major security issue... a regression from Gemini CLI." The issue remains **open** as of this research (last updated 2026-09-04); Google's own proposed fix ("disallow `bypassSandbox` without explicit user confirmation even when `--dangerously-skip-permissions` is enabled; in headless mode, never allow `bypassSandbox`") is not yet shipped.
- **`antigravity-cli#843`** ("`--sandbox` is unusable on Linux..."): on Arch- and Fedora-family Linux (where `/etc/ssl/cert.pem` is a symlink into `/etc/ca-certificates/extracted/`), sandbox construction fails outright at the CA-certificate-install step — **on bare metal, no Docker involved** — because the symlink target directory is read-only inside the sandbox's own mount namespace. Filed against 1.1.13, reproduced by three independent reporters across 1.1.13 → 1.1.22 → 1.1.25 → 1.1.27 (still open, still reproducing as of the most recent 1.1.27 comment: "I use 1.1.27 and arch, I still have the issue"). Reported effect in headless (`-p`) mode: **every** tool call becomes an `unsandboxed` request that headless mode auto-denies, so the CLI cannot execute a single command — the exact same "sandbox construction failed → bypass required → auto-denied in headless mode" shape as the TrueNAS Docker report in §4, but triggered by an OS packaging detail instead of a container capability restriction.

**Confidence: high** that both bugs are real, current (both open), and reproduced by multiple independent reporters with concrete log excerpts — these are primary GitHub-repo sources (the vendor's own issue tracker), even though the reports themselves are user-submitted rather than Google statements.

## 6. This repo's current `setup-antigravity-devcontainer` — what it actually wires up today

Read directly from `skills/setup-antigravity-devcontainer/SKILL.md` and its `templates/` directory on `main`.

- **The YOLO alias does not use `--sandbox` at all.** `templates/yolo-alias-block.sh` defines `alias agy-yolo="agy --mode accept-edits"` — no `--dangerously-skip-permissions`, no `--sandbox`. The template's own comment explains why, citing `antigravity-cli#36` directly: "Do not swap in `--dangerously-skip-permissions --sandbox`... making `--sandbox` a no-op." The real safety boundary this skill relies on instead is a curated `permissions.allow` list in `~/.antigravity/antigravity-cli/settings.json` (SKILL.md step 7: "starting from `git`, `gh`, `ls`, `cat`, never `rm`/`curl`/raw `bash -c`/a wildcard"), set up as a manual, once-per-machine step — this repo's own SKILL.md text notes the settings path as `~/.antigravity/antigravity-cli/settings.json`, which does not match the `~/.gemini/antigravity-cli/settings.json` path found directly on Antigravity's own `/docs/cli/settings` page (§1) or the `/home/vscode/.gemini/antigravity/skills` path used in this same skill's own `templates/post-start-block.sh` for skill-sync. **This is a discrepancy worth flagging to whoever owns this skill** — either the SKILL.md's reported-next-steps path is stale/wrong, or Antigravity accepts both paths for compatibility with its Gemini CLI lineage; this research did not resolve which.
- **`setup-antigravity-devcontainer` never touches the Capability Seam (`runArgs`) at all.** Unlike `setup-codex-devcontainer` (which has an unconditional step 4, "Patch the Capability Seam — unconditional, every run," appending `templates/capability-seam-entries.json` to `devcontainer.json`'s `runArgs` on **every** run regardless of the YOLO-alias answer, because Codex's bubblewrap sandbox "is its normal execution mode, not a YOLO-only feature"), `setup-antigravity-devcontainer/SKILL.md` has no equivalent step — its numbered steps go straight from install-block (step 3) to skill-sync (step 4) to README (step 5) to verify (step 6), with no JSON-array patch step anywhere. **The Capability Seam is currently unused by this skill entirely.**

**Confidence: high** — read directly from the current files on `main` in this worktree.

## 7. The Capability Seam concept, for reference (as defined elsewhere in this repo)

Per `skills/setup-devcontainer/CONTEXT.md`: **Capability Seam** is "the one designated, explicitly-named extension point in `devcontainer.json` (`runArgs`) that a CLI Skill may idempotently append to when it needs elevated container runtime settings — the sole, narrow exception to the Own-Block Contract's 'container definition is base-owned' rule. Today only `setup-codex-devcontainer` uses it." `devcontainer.json`'s `runArgs` field starts as an empty array (`skills/setup-devcontainer/templates/devcontainer.json` line 16) precisely so that a CLI Skill can append there without touching anything else in the base scaffold. Codex's own `templates/capability-seam-entries.json` (referenced, not re-read in full here since it's out of scope for this Antigravity-focused research) is what carries the `cap_add: SYS_ADMIN` / `seccomp=unconfined` / `systempaths=unconfined` settings analyzed in the sibling Codex research file.

## Bottom line for the downstream decision

Antigravity's own docs describe `--sandbox` as intentionally self-contained and host-native by design — it explicitly disclaims needing Docker or a VM to *provide* isolation, using kernel namespaces (Linux), Seatbelt (macOS), or AppContainer (Windows) directly against whatever kernel it's given. But that design goal says nothing about the reverse direction this issue actually asks about: what happens when Antigravity's own sandbox tries to construct *its own nested* namespaces from inside an already-Dockerized devcontainer. Google's docs are silent on that scenario, exactly as they were found to be for Codex. The one piece of direct evidence on that exact scenario — a third party's controlled test of Antigravity 1.1.27 inside a hardened Docker baseline — shows the sandbox failing to construct (`unshare -Ur: Operation not permitted`) and Antigravity falling back to requesting an explicit, user-approved bypass rather than silently proceeding unsandboxed. That failure mode lines up architecturally with what this repo's own Codex/bubblewrap research already found: Docker's default seccomp profile gates the exact `clone`/`unshare`/`mount` syscalls namespace-based sandboxes need behind `CAP_SYS_ADMIN`, which the kernel itself doesn't actually require for unprivileged user namespaces.

Where this diverges meaningfully from the Codex case, though, is that Antigravity's sandbox is currently **not a load-bearing safety mechanism regardless of the container question** — an open upstream bug makes it a no-op precisely in the unattended/skip-permissions mode any YOLO alias would use, and a second, separately-open bug breaks it outright on a whole family of Linux distros with no container involved at all. This repo's `setup-antigravity-devcontainer` skill has already, independently, reached the same conclusion in practice: its YOLO alias never uses `--sandbox` (its own template comment cites the `#36` bug by name), and unlike `setup-codex-devcontainer` — which unconditionally grants Codex's bubblewrap sandbox the Capability Seam because bubblewrap **is** Codex's normal execution mode — `setup-antigravity-devcontainer` never touches the Capability Seam (`runArgs`) at all. There is currently no capability grant to loosen for Antigravity, and nothing in this research suggests one would currently be worth adding: even if the Shared Container's `runArgs` were widened to let Antigravity's sandbox actually construct its namespaces, the `#36` bug means that grant would buy no real protection in the unattended path this skill's YOLO alias targets. If a future Shared-Container-level network/filesystem baseline is added by `setup-devcontainer`, it should be designed around what the container itself needs to enforce directly (the model this repo already uses for Codex, where bubblewrap's namespace needs are real and load-bearing) — not around preserving headroom for Antigravity's own `--sandbox` to work, since that flag is not currently a mechanism worth protecting.

One accuracy note surfaced along the way, unrelated to the sandbox mechanism itself but worth relaying to whoever owns this skill: `setup-antigravity-devcontainer/SKILL.md`'s reported next-steps path for the curated `permissions.allow` list (`~/.antigravity/antigravity-cli/settings.json`) does not match the settings path found directly on Antigravity's own current docs (`~/.gemini/antigravity-cli/settings.json`) — this research did not resolve which is authoritative.
